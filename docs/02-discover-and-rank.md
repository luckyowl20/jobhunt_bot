# 02 — Discover, validate, and rank jobs

**Inputs:** approved profile/preferences, evidence, resume bases, workbook template, and prior-job history. **Outputs:** `workbooks/new_jobs.xlsx`, research decisions, and a verified history append. Use `templates/workbook-schema.md` as the field contract.

1. Read the saved context and identify changed facts or preferences. Create `outputs/YYYY-MM-DD_HHMMSS_<random>/` and a manifest using the template. Snapshot configuration and input versions. Record the user's timezone.
2. Read every worksheet in the history and template. Build duplicate keys from employer + requisition ID; also compare canonical URLs and normalized employer/title/location. Strip tracking parameters but retain parameters that identify the job. Treat substantially identical reposts as duplicates unless documented as a genuinely different opening. Check duplicates within the new batch too.
3. Search the enabled lanes using role synonyms and evidence-backed skills. Evaluate more candidates than the target count where available. Aggregators may reveal leads; follow them to the hiring organization's exact page. Accept employer-hosted ATS pages after verifying the employer relationship. Do not use a search results page as a posting.
4. Open each exact posting and record employer, title, location, work arrangement, requisition, responsibilities, required versus preferred qualifications, compensation if stated, start/closing dates, official URL, check time, and activity evidence. A working Apply action or clearly open posting is evidence; an HTTP success or search snippet alone is not. Generic redirects, closed listings, talent pools, and inaccessible pages are not verified openings.
5. Apply hard scope gates: location/remote eligibility, excluded offices, role family, seniority, employment type, start date, and any stated non-negotiable requirement. Compare material requirements to evidence IDs. Unknown citizenship, sponsorship, licenses, or clearance are unresolved gates, not positive matches. Put such roles in `research/conditional-jobs.md` pending clarification, outside the accepted count. Do not apply preferred qualifications as mandatory gates.
6. Rank eligible roles by the saved rubric. Default: core-work evidence 0–5 weighted 50%, desired role/industry 0–5 weighted 25%, location/work arrangement preference 0–5 weighted 15%, learning/career alignment 0–5 weighted 10%. Score = sum(weight × rating/5), out of 100. Use brief evidence-based explanations for each rating; it is a prioritization aid, not a hiring probability. Break ties by core-work evidence, then user location preference, then employer/title for stable ordering. The original workbooks used ordinal priority and qualitative match; the numeric rubric is a configurable addition.
7. Select the strongest target number without weakening gates. If fewer qualify, save the validated subset and explain the shortfall. Ask before broadening scope; do not add remote, operations, senior, or weakly related jobs just to fill ten. Lanes need not have equal representation.
8. For each accepted role, choose a source resume base and give specific tailoring recommendations: relevant evidence IDs, projects, technologies, keywords, and possible bullet changes. A note suggesting an unsupported claim does not authorize that claim. Leave contact columns empty in `jobs-only`.
9. Create the workbook preserving template layout, styles, formulas, row heights, widths, filters, links, and frozen panes. Replace only example rows; keep unrelated sheets. Normalize geography headers for the new user. Record rejections and reasons separately so excluded leads do not pollute the accepted-job history.
10. Reopen and inspect the workbook, including full cell contents. Check row counts, unique keys, official links, gate evidence, ranking explanations, formula errors, wrapping, and correct blank contacts. Recheck activity before finalizing and before later tailoring if time has passed.

## Append transaction

Once the entire accepted set passes validation, back up the existing history into the run's QA directory. Stage an updated copy, append accepted jobs once, and verify prior rows are unchanged and the row-count increase equals the accepted count. Store job keys, run ID, and append status in the manifest (or a sidecar if the legacy history has only two columns).

Before replacing the private history, verify it has not changed since the snapshot. If it changed, merge against the current file and deduplicate again. Never overwrite another session's updates. Reopen the committed file and record pre/post counts. Re-running a stage must be idempotent: an already-appended run adds zero duplicates. In upload mode return the updated history separately and instruct the user to replace the saved copy. A conditional/rejected role belongs in research notes, not the accepted set.
